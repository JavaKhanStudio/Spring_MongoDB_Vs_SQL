RepèreLes deux schémas, en vis-à-vis

Le même domaine : une tortue, ses mensurations, ses observations de terrain, ses tags, son habitat, ses programmes de recherche. À gauche il devient six tables et 1 296 lignes ; à droite, trois collections et 141 documents. Le domaine couvre exprès les cinq formes de relation, pour que chacune ait son vis-à-vis document.

Le modèle document ne supprime pas la complexité, il la déplace : trois tables, deux clés étrangères et toutes les jointures disparaissent — et la cohérence, elle, devient la responsabilité de l'application.

L'ObjectId, en douze octets

6a95afcd  80116a8f92  f32aaf
└─ date ┘ └─ hasard ┘ └ cpt ┘
 4 octets   5 octets   3 octets

Il porte sa date de création — trier par _id, c'est presque trier par date. Et il est généré par le client, sans aller-retour, là où un AUTO_INCREMENT doit être attribué par le serveur.

Le détail qui surprend

BSON n'a pas de type « date sans heure ». Un LocalDate du 14 mars est stocké en instant UTC — et ressort daté du 13 à 23 h en heure de Paris. Stockez des Instant, ou une chaîne yyyy-MM-dd quand seule la date compte.

Le schéma n'a pas disparu : il a changé de place. Il est passé du moteur vers votre code — plus souple, et entièrement sous votre responsabilité.

Chapitre 2Embedding ou reference

C'est la décision de modélisation, et elle se prend champ par champ. Voici la même lecture — une tortue avec ses observations — dans les deux modèles.

La question qui tranche

La règle — et le fait qu'elle s'applique champ par champ

On privilégie l'embedding quand les données appartiennent au même agrégat métier, sont généralement lues ensemble, et ont un cycle de vie commun. La formule qui circule chez les praticiens MongoDB la résume bien : « data that is accessed together should be stored together ».

On l'évite dès que la duplication devient coûteuse à maintenir. Si 100 000 utilisateurs partagent la même entreprise, embarquer sa fiche complète, c'est la dupliquer 100 000 fois — et la maintenir autant de fois. L'entreprise ayant sa propre existence, une référence vers son identifiant s'impose.

Le piège est de croire que la décision se prend par entité. Elle se prend par champ — et l'habitat le démontre à lui seul, en tranchant dans les trois sens à la fois :

Champ de l'habitat Traitement Pourquoi
name copié dans chaque tortue change une fois par décennie, affiché partout
waterTempC non copié c'est une mesure : elle change tout le temps
l'objet entier jamais embarqué 16 tortues le partagent, il a sa vie propre

Le critère est un produit : fréquence de mise à jour × nombre de copies à propager. Un nom d'habitat, c'est « rare × 16 » — on copie. Une température, « permanente × 16 » — on ne copie pas. À 100 000 copies, le calcul penche bien plus vite.

La même opération SQL MongoDB
Lire les tortues d'un habitat avec sa température 1 requête (join fetch) 2 requêtes — la température n'est pas copiée
Changer la température 1 update, 1 ligne 1 $set — 1 document, 0 tortue
Renommer un organisme (champ copié) 1 update, 2 lignes 2 updates + 52 copies

Les deux premières lignes se lisent ensemble : côté document on a refusé de payer à l'écriture, donc on paie à la lecture. La troisième montre le choix inverse, pris sur un autre champ de la même base. Aucun modèle ne gagne — ils déplacent le coût. Modéliser, c'est choisir de quel côté payer, en connaissant ses lectures.

Et @DBRef ?

Il stocke { $ref, $id } et Spring Data résout la référence à la lecture. Sur la liste complète, mesuré dans le projet : 12 requêtes pour douze tortues — et le même habitat rechargé autant de fois qu'il est référencé, sans aucun cache.

Surtout, @DBRef n'existe pas côté serveur : aucun $lookup, aucun filtre, aucun tri ne peut porter sur l'objet lié. Préférez une manual reference — en n'oubliant pas de la stocker au bon type : 

@Field(targetType = FieldType.OBJECT_ID)   // ← sans ça, $lookup ne trouvera jamais rien
private String habitatId;

Plusieurs-à-plusieurs : la table qui disparaît

Une tortue suit plusieurs programmes de recherche, un programme suit plusieurs tortues. C'est la seule relation du projet qui produise, côté relationnel, une vraie table de jointure — et la seule qui n'ait aucun équivalent côté document.

La relation vit entre les deux

turtle_program
  turtle_id   FK → turtle.id   ┐ PRIMARY KEY
  program_id  FK → program.id  ┘ composite

-- inscrire :
insert into turtle_program
  (turtle_id, program_id) values (?, ?)

Ni la tortue ni le programme ne sont modifiés. Les deux sens de lecture coûtent pareil, et la clé primaire composite interdit la double inscription.

La relation vit d'un seul côté

// dans le document tortue
"programs": [
  { "programId":    ObjectId("…"),
    "name":         "Argos Océan Indien",
    "organisation": "CNRS" } ]

// inscrire :
{ $addToSet: { programs: { … } } }

Un seul document touché. $addToSet joue le rôle de la clé primaire composite — mais rien ne garantit que l'identifiant existe.

La même question SQL MongoDB
Les programmes d'une tortue 2 requêtes — jointure turtle_program → program le document les contient déjà (+1 $in pour les libellés)
Les tortues d'un programme (35) 1 requête — on filtre sur program.name 1 requête — grâce au nom recopié (2 par la référence seule)
Les tortues du CNRS (52) 1 requête, 2 jointures — rien de dupliqué 1 requête, 0 jointure — parce que l'organisme est dupliqué
Renommer un organisme 1 UPDATE, 2 lignes 2 écritures : 2 sources, puis 52 copies
Inscrire une tortue 1 INSERT dans la table de jointure 1 $addToSet sur la tortue
Combien de tortues par programme GROUP BY sur la table de jointure $lookup dont le foreignField est un tableau
Ce que la contrainte garantissait, et qui devient votre travail

La clé primaire composite empêchait la double inscription → côté document, c'est $addToSet qui s'en charge. La clé étrangère empêchait de référencer un programme inexistant → rien ne l'empêche côté document. Le ON DELETE CASCADE nettoyait la table de jointure → il faut désormais un $pull sur toutes les tortues concernées, à écrire soi-même.

La duplication, choix de conception plutôt que faute

Le tableau ne contient pas des identifiants nus : chaque élément porte l'identifiant plus une copie du nom et de l'organisme. C'est le motif de l'extended reference — et c'est ce qui permet de répondre à « toutes les tortues du CNRS » (52 individus, répartis sur deux programmes) en une requête, sans jointure ni $lookup.

Un programme a quinze champs : acronyme, responsable scientifique, budget, site web, description de plusieurs lignes, protocole de terrain imbriqué, statut, années de début et de fin… La copie n'en emporte que deux. C'est là que la dénormalisation se distingue de la duplication naïve : on ne recopie pas l'entité, on recopie l'étiquette qu'on affiche. Appelez /api/mongo/programs/of-turtle/{id} et comptez les champs de la réponse : trois, contre quinze pour son jumeau SQL. Les douze autres sont restés dans la collection programs.

Normaliser, puis joindre

-- lire : 1 requête, 2 jointures
where p.organisation = 'CNRS'

-- renommer : 1 ligne, et c'est tout
update program
   set organisation = ?
 where organisation = ?

L'organisme n'existe qu'à un endroit. On peut interroger n'importe quel attribut de n'importe quelle table sans l'avoir prévu à la modélisation.

Dupliquer, puis lire d'un trait

// lire : 1 requête, 0 jointure
{ "programs.organisation": "CNRS" }

// renommer : 2 écritures
db.programs.updateMany(…)
db.turtles.updateMany(
  { "programs.organisation": "CNRS" },
  { $set: { "programs.$[e].organisation": … } },
  { arrayFilters: [ { "e.organisation": … } ] })

52 documents touchés, une fenêtre d'incohérence entre les deux écritures, et rien dans le moteur pour imposer la seconde.

La nuance qui compte

Dupliquer n'est pas interdit en SQL — entrepôts de données, tables de report, vues matérialisées le font tous les jours. La différence est ailleurs : en SQL la jointure est bon marché et correcte, donc la duplication reste une optimisation de dernier recours, et le moteur offre des outils pour la tenir à jour (vue matérialisée, trigger, colonne générée, ON UPDATE CASCADE).

En modèle document, la duplication est un choix de conception assumé, prévu dès la modélisation — et il n'existe aucun mécanisme pour la propager : c'est votre code, à chaque endroit où la source change.

D'où le critère, et il est simple : on ne duplique que ce qui est stable et lu souvent. Un nom d'organisme change une fois par décennie et s'affiche à chaque écran — bon candidat. Un poids qui change à chaque pesée — mauvais candidat. Et on garde toujours la référence à côté de la copie : programId reste la source de vérité, la copie n'est qu'un raccourci de lecture.

Le choix du côté qui porte la relation n'est pas neutre : ici « les programmes d'une tortue » est gratuit. Si le besoin dominant était l'inverse, on stockerait turtleIds côté programme — ou les deux, au prix de deux écritures à garder cohérentes, sans transaction pour l'imposer.

Chapitre 3Repository ou Template

MongoRepository est construit au-dessus de MongoTemplate : même connexion, même convertisseur. Les mélanger dans un même service est l'usage normal, pas un compromis.

Pourquoi save() ne suffit pas

Même intention — corriger un poids — et voici ce qui part réellement sur le réseau :

repository.save(tortue)

{ "update": "turtles",
  "updates": [{
    "q": { "_id": … },
    "u": { "_id": …,
           "name": "Crush",
           "species": "Chelonia mydas",
           "tags": [ … ],
           "measurements": { … },
           "observations": [ … ],
           … } }] }

Une lecture, puis le document entier réécrit. Tout ce qu'un autre client aurait modifié entre-temps est écrasé au passage.

2 allers-retours

template.updateFirst($set)

{ "update": "turtles",
  "updates": [{
    "q": { "_id": … },
    "u": { "$set": {
             "measurements.weightKg": 140.0
    } } }] }

Aucune lecture préalable, un seul champ sur le réseau, et rien d'autre n'est touché dans le document.

1 aller-retour

Le piège caché

Le même problème existe en JPA — mais Hibernate le masque : le dirty checking n'écrit que les colonnes modifiées. Spring Data Mongo, lui, ne suit pas les objets. D'où l'importance de connaître le MongoTemplate.

Figé à la compilation → repository. Dynamique, partiel ou atomique → template. Les 20 % de cas qui relèvent du template sont précisément ceux où une mauvaise solution fait mal en production.

Chapitre 4Requêtes et projections

La bonne nouvelle : les signatures sont identiques dans les deux mondes. Seule la traduction change.

JPA

List<Turtle> findBySpecies(String s);

→ select … from turtle where species = ?

MongoDB

List<Turtle> findBySpecies(String s);

→ { "species": "Chelonia mydas" }

Le point du nom de méthode devient le point du chemin BSON : findByMeasurementsShellLengthCmGreaterThan donne { "measurements.shellLengthCm": { "$gt": 90 } }. Et sur un tableau, l'égalité signifie « contient » — { "tags": "balise-argos" } sélectionne les documents dont le tableau contient cette valeur.

L'erreur silencieuse à montrer en cours

Le champ Java birthYear est stocké sous le nom annee_naissance (@Field). Alors : 

findByBirthYearLessThan(int year)              ✅  nom JAVA
@Query("{ 'annee_naissance': { $lt: ?0 } }")   ✅  nom STOCKÉ
@Query("{ 'birthYear': { $lt: ?0 } }")         ❌  zéro résultat, aucune erreur

Le JSON d'un @Query part tel quel vers le serveur : Spring Data n'y traduit pas les noms de champs. La derived query, elle, passe par le mapping.

Trois projections, trois coûts

Forme Ce que le serveur envoie Filtré par
Interface fermée 2 champs — Spring Data ajoute "projection": { name: 1, species: 1 } MongoDB
Interface ouverte @Value tout le document — l'expression SpEL peut tout toucher l'application
DTO record les champs du record, comme l'interface fermée MongoDB
findAll() puis .map() tout le document l'application

Sur douze tortues, aucune importance. Sur une collection réelle, c'est la différence entre quelques kilo-octets et plusieurs méga-octets par requête.

Derived query tant que le nom reste lisible, @Query quand le filtre devient précis, MongoTemplate quand il devient dynamique. Et une projection dès que l'écran n'affiche que trois champs.

Chapitre 5Le pipeline d'agrégation

En SQL on décrit le résultat et le moteur choisit son plan. En MongoDB on décrit une suite d'étapes : chacune reçoit un flux de documents et en produit un autre.

Le dictionnaire

Étape Équivalent SQL Rôle
$matchWHEREfiltrer
$projectSELECTchoisir, renommer, calculer
$groupGROUP BY$sum · $avg · $min · $max · $push
$sortORDER BYtrier
$limit / $skipLIMIT / OFFSETpaginer
$lookupLEFT JOINjoindre une autre collection
$unwindaucundéplier un tableau en N documents
$bucketCASE WHEN + GROUP BYhistogramme
$out / $mergeCREATE TABLE AS SELECTécrire le résultat
Trois pièges du $lookup

1. Le résultat est un tableau (0, 1 ou n éléments) : on enchaîne presque toujours sur un $unwind. 2. $lookup + $unwind se comporte comme un INNER JOIN — les documents sans correspondance disparaissent ; pour un LEFT JOIN, preserveNullAndEmptyArrays: true. 3. Les types doivent correspondre : une référence stockée en chaîne ne matchera jamais un _id de type ObjectId. Sans erreur — juste zéro résultat.

Le pipeline n'est pas « le SQL de MongoDB », c'est une chaîne de transformations. Un GROUP BY s'y traduit sans effort ; en échange on obtient $unwind, $bucket, $facet et $graphLookup — des choses que le SQL standard ne fait pas, ou très mal.
